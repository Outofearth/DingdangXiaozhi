# 技术架构与设计取舍

这份文档记录**为什么这么写**，而不是逐行解释代码。适合想改它、或者在自己设备上复刻的人。

---

## 1. 整体分层

```
┌──────────────────────────────────────────────────────────┐
│  MainActivity        UI + 语音意图分发 + 清单编排          │
│    ├─ VideoActivity        视频页（独立 Activity）        │
│    ├─ SettingsActivity     设置                          │
│    ├─ ChatManagerActivity  聊天记录管理                   │
│    └─ FloatEntryService    待机悬浮入口                   │
├──────────────────────────────────────────────────────────┤
│  会话层   XiaoZhiClient（WS）· AudioCapture · AudioPlayer  │
│           OtaClient（绑定）· McpHandler（工具调用）        │
├──────────────────────────────────────────────────────────┤
│  媒体层   MediaSurvey（清单）· FileMusicPlayer（本机）     │
│           RemoteLibrary（SMB）· NetDiskLibrary（网盘）     │
│           SmbStreamSource / OlStreamSource（边下边播）     │
├──────────────────────────────────────────────────────────┤
│  基础设施 VolumeCtl · StorageCtl · PlayMode · LocalFiles   │
│           SyncManager（P2P 同步）· ChatStore（SP 存储）    │
└──────────────────────────────────────────────────────────┘
```

没有用 Gradle、没有用 AndroidX、没有用 Kotlin。原因见第 9 节。

## 2. 音频链路

### 上行

```
AudioRecord(16 kHz, mono, PCM16)
  → 每 60 ms 一帧
  → opus_encode（JNI，libopus 1.3.1 浮点）
  → WebSocket 二进制帧（裸 Opus，无自定义头）
```

**裸帧**是关键：官方固件在 Opus 数据前不加任何头，直接把这个帧当作一个完整的 Opus packet 解。
早期版本加了 16 字节长度头，服务端能连上但识别不出声音。

### 下行

```
WebSocket 二进制帧（24 kHz 裸 Opus）
  → opus_decode
  → AudioTrack（STREAM_MUSIC）
```

上下行采样率不同（16 k / 24 k）是服务端的约定，解码器要按 24 k 初始化。

### 为什么原客户端不行

官方 Flutter 客户端在 Android 8.1 上打开 `AudioRecord` 后，Flutter 的录音插件不读缓冲区，
HAL 灌数据但 `Server=0`，上行永远是静音。这块板子的 MIC 源本身是好的（`audio_flinger` 显示正常灌帧），
所以换原生实现即可，不需要动固件。

## 3. 语音意图分发：本地优先

用户说的一句话，先过**本地**，本地接不住才发给云端：

```java
onAsr(text) {
    if (handleVolumeIntent(text))     return;  // 音量：纯本地，改完就回
    if (handleVideoVoiceIntent(text)) return;  // 视频页的暂停/快进/退出
    if (handleLibraryQuery(text))     return;  // 「有哪些歌」类清单问句
    if (tryLocalPlay(text))           return;  // 点播：本机/共享/网盘/缓存
    if (handleFileIntent(text))       return;  // 文件增删类指令
    sendTextToCloud(text);                     // 都不是 → 交给云端对话
}
```

这么排的直接收益：**调音量、暂停、点播不会打断云端正在进行的回答**，也不会被云端「复述」一遍。
反过来，一旦送云端，本地就把正在播的东西先让开（记断点、暂停），答完再接回去。

### 清单为什么要「本地生成」

如果让云端回答「你有哪些歌」，它只能复述 App 通过 MCP 工具报给它的内容，
而大模型的复述格式不可控：会把一行一条念成一整段、序号会重排、条数会漏。

所以清单由本地拼装、本地播报、本地留一份带序号的副本（`lastSurvey`，3 分钟有效）。
云端那边只负责念一句开场白。用户说「播放第 3 个」时，本地直接按自己的副本取第 3 项——
那句话里根本没有歌名，云端什么也做不了。

### 清单版式规则

- **一行一条，序号全局连续**（跨来源分组，不重新从 1 开始）
- 组标题带数量：`共享文件夹 30 个：`
- 屏幕全列，**语音只念前 10 条**，剩下补一句「后面还有 N 个，都列在屏幕上了」
- 兜底断行：任何来源的文本只要出现序号或 ≥4 个顿号，就强制拆行（`MediaSurvey.reflowNumbered`）

## 4. 四个播放源怎么统一

四种来源的物理形态完全不同（文件、SMB 共享、HTTP 网关、本地缓存），但对外都实现同一个接口：

```java
public interface PlayItem {
    String source();        // 交给播放器的地址
    String displayTitle();  // 显示名
}
```

`MediaSurvey` 依次收集，去重（同名的本机文件与共享文件只列一次，并说明「另有 M 个别处已有」），
然后统一编号。

### 名字匹配：打分制，不是包含匹配

用户说「播放孤单背影」，库里同时有《孤单背影》和《孤山孤…DJ 版》。
朴素的做法（`contains`）会选中先遍历到的那首 —— 表现是「点了 A 放了 B」。

`LocalFiles.aliasScore(spoken, name)` 给候选打分：

| 情况 | 加减分 |
|---|---|
| 整句完全命中 | `4 × 字数`（压倒性） |
| 别名就是整句话 | `+14` |
| 只是 2 字别名命中 | `-4`（避免「禅乐」误配到长名字） |
| 同音匹配 | `3 × 连续同音音节` |
| 总分 < 6 | 不算命中 |

再叠一条规则：**当前目录优先**。人在某个文件夹里说歌名，先在这个文件夹里找，
找不到才退到全量索引。这条规则修掉了「明明进了 CD01，却放了别的目录里的同名歌」。

中文还多一层：繁简混用。`TS_PAIRS` 把常用繁体字映射成简体再比，否则
`《以後的以後》` 和「以后的以后」永远对不上。

## 5. 边下边播：两条链路，同一套思路

### 为什么不能直读 SMB

SMB 每次读取都是一次网络往返。音频播放器每次只要几 KB，请求一多，吞吐就被往返次数拖死
（实测某台设备上只有 0.67 MB/s，单次读最长 1419 ms）。
只要单次读耗时超过音频缓冲区能撑的时间，`AudioTrack` 就会 underrun —— 听感是「mp3 一断一断」。

注意：**mp4 不卡不能反证网络好**。视频播放器一次读几百 KB，往返摊薄了；
而缓存又厚，卡一下你根本看不出来。

### 方案：后台顺序下载 + 播放器读本地

```
播放器 readAt(pos)
   ├─ pos 在已下载区间 → 直接读本地 part_ 文件
   ├─ pos 在前方  → 阻塞等预取线程追上
   └─ pos 在后方（用户拖了进度）→ 开独立连接 Range 请求那一段
```

两条链路（`SmbStreamSource` / `OlStreamSource`）结构完全一致，差异只在「怎么取数据」：

| | SMB | 网络盘 |
|---|---|---|
| 取数 | jcifs 顺序读 | HTTP Range |
| 精度 | 字节 | 字节（206 响应） |
| 特殊处理 | 无 | 内存预取 512 KB，窗口向 `position` 前扩一半 |

那个「向前扩一半」是踩出来的：mp4 的 `moov` 索引常在文件**尾部**，
播放器一上来就跳到末尾读索引，然后往回读。预取只往后看时，
前 40 次 read 全落空，卡在「正在缓冲」20 秒；窗口向前扩一半后 2–3 次请求就起播。

### 下完立刻改名

下载完成时把 `part_<ts>_<name>` 立刻 `rename` 成 `smb_<ts>_<name>`（或 `ol_`）。
**不能等 close 时再改**：下一首起播会调 `cleanParts()`，把所有 part_ 删掉，
如果那时 rename 还没发生，正在播的文件就没了。

## 6. 缓存三层

| 前缀 | 内容 | 策略 |
|---|---|---|
| `smb_` / `ol_` | 下完的整包 | 两前缀**合算**一个 600 MB LRU |
| `part_` | 边下边播的未完成分片 | 清理时跳过 3 分钟内写过的 |
| `music/*.pcm` | 云端曲库 | 无上限，手动清 |

索引文件特意命名成 `olidx.tsv` —— **绝不能以 `ol_` 开头**，
否则会被缓存清理当成网盘缓存删掉，表现出来是「索引莫名其妙变回 0 条」。

## 7. 只有一路声音

设备只有一个音频输出。视频页和 TTS、视频页和音乐，必须互斥。

- `VideoActivity` 用 `singleTask`，避免叠出两个实例同时放
- 起音频前先广播让视频页退出
- 视频页 `onPause` 自己暂停，并广播 `back` 让主界面恢复 TTS 出声
- 主界面收到「视频在前台」时，把 `AudioPlayer` 静音而不是停掉（停掉再恢复会有断点）

## 8. 网盘索引：BFS + 落盘续跑

需求是「说个名字就能放」，这要求遍历整个网盘拿到全部文件名。但网盘有两类极端目录：

- 根层 22 个文件夹、0 个散落文件
- 某个目录单层 1677 个文件，列一次要 4.2 秒

一次性递归扫描的问题：扫得慢、一重启就白扫、超出上限的文件永远「说名字点不到」。

改成：

```
每趟：从队列取最多 40 个目录，跑满 5 秒就停
      → 把已列目录 + 已收文件写进 files/olidx.tsv（先写 .tmp 再 rename）
      → 歇 800 ms 让出带宽（别影响正在播的流）
      → 下一趟接着来
```

- 每趟结束都落盘，所以**随时可以中断、重启继续**，越用越全
- 队列空时写一个 `C` 标记表示扫完；30 分钟后自动重扫
- 实测整个库 8970 条 / 206 个目录 / 8 趟约 40 秒；重启读盘 < 1 秒

一个自埋的坑：`list()` 在并索引时忘了先 `loadIndex()`，
结果 `saveIndex()` 用「刚浏览的几条」把整份索引覆盖了（8970 → 3）。
现在 `list()` 开头必 `loadIndex()`，`saveIndex()` 里加 `if (!indexLoaded) return` 双保险。

### 目录导航 vs 全量索引

两条线各管一件事：

- **清单**（用户翻目录）：只列**当前这一层**，一层一层翻。压平成一份大列表念不完（第二层就 2676 个文件）。
- **索引**（用户说名字）：全量 BFS，负责「直达」。

文件夹条目**不参与跨来源去重** —— 一旦被「同名已存在」吞掉，用户就永远进不去那个目录。

## 9. 为什么不用 Gradle

目标环境是离线 + 老 SDK，Gradle 会带来一堆不必要的复杂度：

- `maven.google.com` 在当时的网络下 502，AGP 拉不下来
- 依赖只有 5 个 jar（okhttp / okio / jcifs-ng / slf4j / bcprov），全部静态引用
- 需要在 Windows Git Bash 下可复现，构建时间要短

所以 `build.sh` 手写了 aapt2 → javac → d8 → zipalign → apksigner 全流程，
一次完整构建约 30 秒。代价是要自己管 `R.java` 和依赖版本，收益是完全可控、无网络依赖。

`AppConfig.java` 由构建脚本生成（区分 `speaker` / `mobile` 两个目标），不要手改。

## 10. 线程模型

- **一个主线程**做 UI，所有回 UI 的更新走 `ui.post(...)`
- **一个 WS 线程**（`XiaoZhiClient` 内部）收消息，回调里只做分发，不阻塞
- **录音线程**持续推 Opus 帧
- **下载线程**每首歌一个（`SmbStreamSource` / `OlStreamSource` 内部）
- **索引扫描**低优先级线程，每趟 5 秒主动让出
- 网络类调用（列目录、探测、播放地址）**绝不在主线程**

设备内存只有约 1 GB，进程 PSS 控制在 70 MB 以内；索引常驻内存约 5 MB。

## 11. 调试与排障设施

发布版保留了这些（不影响正常使用，排障离不开）：

- `persistStatus(text)` → 追加写 `files/status.txt`。这台设备的固件屏蔽了 `Log.d`，
  `logcat` 经常什么都看不到，只能落盘再 `adb pull`
- 视频页的状态行、清单的「正在执行 xxx」提示 —— 设备上没有 Toast，反馈必须落在界面或聊天流里
- 控制台页（设置 → 控制台）集中显示连接与绑定状态

## 12. 想移植到别的设备

按改动量从小到大：

1. **分辨率 / 方向**：`res/layout` 里都是相对布局，主要调字号与 `player` 区域宽高
2. **音频参数**：`AudioCapture` 的采样率、帧长；`AudioPlayer` 的 24 kHz 输出
3. **音量档位**：`VolumeCtl` 里 `STREAM_MUSIC` 的 max index（本机是 15，其他设备不同）
4. **悬浮入口**：`FloatEntryService` 的窗口类型与权限申请方式
5. **开机自启**：`BootReceiver` 在某些 ROM 上需要额外的自启白名单

详见 [构建与适配.md](构建与适配.md)。
